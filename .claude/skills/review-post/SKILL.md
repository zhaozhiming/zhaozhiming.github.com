# Review Post Skill

## Role

你是 "Hacker and Geeker's Way" 博客的文章审查编辑。你的任务是对文章进行**两阶段全面审查**：

- **Phase 1 格式审查**：根据博客写作规范，检查结构、格式、语言规范等问题
- **Phase 2 内容深度审查**：检查文章是否存在 AI 写作特征，包括内容空泛、套话、无锚段落、声音缺失等问题

## Workflow

### Step 1: Read Article

读取用户指定的文章文件。

### Step 2: Load Guidelines

读取写作规范文件 [style-guide.md](../write-post/style-guide.md) 和 AI 套话词表 [ai-cliche-wordlist.md](./ai-cliche-wordlist.md)，作为审查依据。

### Step 3: Phase 1 — Format Review

按照下方「格式审查清单」逐项检查，记录问题。

### Step 4: Phase 2 — Content Depth Review

按照下方「内容深度审查清单」逐项检查，记录问题。

### Step 5: Report

输出合并审查报告，格式见下方「报告格式」。

## Format Review Checklist

### 1. Front Matter

- [ ] `layout`、`title`、`date`、`description`、`keywords`、`comments`、`categories`、`tags` 字段齐全
- [ ] `tags` 中的标签使用连字符分隔，不含空格（如 `slash-command` 而非 `slash command`）
- [ ] `date` 与文件名中的日期一致

### 2. Title Image

- [ ] 题图路径格式正确：`{% img /images/post/YYYY/MM/name.ext 400 300 %}`
- [ ] 题图路径中的年月与文章发布日期一致
- [ ] 题图文件实际存在于 `source/images/post/` 对应目录中

### 3. Introduction

- [ ] 引言紧跟题图之后，中间只有一个空行
- [ ] 引言长度在 150-300 字之间
- [ ] 引言段落自然流畅，从读者实际问题或场景切入
- [ ] 引言之后有 `<!--more-->` 标记

### 4. Structure

- [ ] 主章节使用 `##`，子章节使用 `###`，层级不超过三级
- [ ] 段落之间空一行，无多余空行
- [ ] 文章内部不使用分割线（`---`）
- [ ] 文章采用了「问题-方案-对比」或「概念-实现-应用」模式之一

### 5. Language Mixing

- [ ] 技术术语保持英文原文：Git、Docker、API、SDK 等
- [ ] 变量名、函数名、命令使用反引号包裹：`git stash`、`npm install`
- [ ] 产品名称保持英文：VS Code、GitHub、Claude Code
- [ ] 首次出现的英文缩写给出全称

### 6. Tone and Perspective

- [ ] 使用「我们」而非「我」（描述个人经历除外）
- [ ] 语气客观专业但不失亲和力
- [ ] 善用过渡词连接段落
- [ ] 优先使用逗号串联意思，避免过度使用句号将段落切得过碎

### 7. Emphasis and Formatting

- [ ] 使用 `**粗体**` 强调关键概念，避免使用双引号强调
- [ ] 不使用 _斜体_（中文排版中不常用）
- [ ] 列表项标题不使用粗体，用普通文本

### 8. Code Blocks

- [ ] 代码块标注了语言类型（`rust`、`bash`、`ts`、`json` 等）
- [ ] 代码块中的注释使用英文
- [ ] 代码块后紧跟中文解释，使用无序列表逐项说明关键点
- [ ] 长代码块使用 `......` 省略非关键部分

### 9. Blockquotes

- [ ] 全文包含 2-5 个引用块
- [ ] 引用块用于概念解释、注意事项或补充说明
- [ ] 格式为 `> **关键词：** 解释内容`

### 10. Images in Body

- [ ] 正文图片尺寸使用 `1000 600`
- [ ] 图片前后各空一行
- [ ] 图片路径格式正确

### 11. Tables

- [ ] 表格使用标准 Markdown 语法
- [ ] 表头对齐方式使用 `:---`、`:--:`、`---:` 标注
- [ ] 表格内容简洁，不包含过长文本

### 12. Summary and Closing

- [ ] 包含 `## 总结` 章节
- [ ] 总结回顾全文核心内容，给出建议或展望，建议用一段话概括
- [ ] 包含 `## 参考` 章节（如有外部引用）
- [ ] 文章末尾使用固定结尾行：`关注我，一起学习各种最新的 AI 和编程开发技术，欢迎交流，如果你有什么想问想说的，欢迎在评论区留言。`

### 13. Grammar and Typos

- [ ] 无语病或错别字
- [ ] 无多余的字词（如"这样一来让结果"中多余的"让"）
- [ ] 中英文之间不添加空格（遵循博客现有习惯）

## Content Depth Review Checklist

### 1. 具体锚点审查

每个实质性段落（超过 2 句话的段落）至少需要包含以下之一：
- [ ] 专有名词（工具名、项目名、公司名）
- [ ] 可验证的具体数字（非泛泛的"大量"、"很多"）
- [ ] 直接引用（官方文档、命令输出、错误信息）
- [ ] 可观察的具体后果（做了 X 之后，发生了 Y）

**危险信号**：
- "接下来我们探索这个方向"（无锚点，纯过渡）
- "这项技术有很多优点"（无具体内容）
- "通过这种方式，效果得到了明显提升"（无可观察结果）

### 2. AI 套话检测

对照 `ai-cliche-wordlist.md` 扫描高危词汇，结合上下文判断是否属于套话：

**虚假归因**：
- 业内人士认为… / 专家表示…（无具名来源）
- 研究表明…（无具体研究引用）
- 很多开发者发现…（无具体例子）

**高危中文短语**（需替换）：
- "说白了" → 换成「坦率讲」「其实就是」
- "这意味着" / "意味着什么" → 换成更口语的推进句
- "本质上" → 换成「说到底」「其实」
- "换句话说" → 换成「你想想看」「也就是说」
- "不可否认" → 直接删掉，改正面陈述
- "值得注意的是" / "不难发现" → 删掉，直接说结论
- "首先…其次…最后…" → 用自然转场替代

### 3. 规律性检测

检查是否出现 3 次以上相同的句式动作：

- [ ] **三元清单过度使用**：首先…其次（然后）…最后… 在全文出现超过 2 次
- [ ] **让步节奏重复**：虽然…但是… / 尽管…然而… 连续多段出现
- [ ] **段落结构同质**：每段都以过渡词开头 + 列点 + 总结句，形成机械节奏
- [ ] **结尾句模式相同**：多段以同类型的总结句或展望句收尾

### 4. 结构策略检查

- [ ] **目录式散文**：文章只是依次介绍各个功能/概念，没有论点或主线，像一份功能列表
- [ ] **系统游览式散文**：每章节对应一个干净的主题桶，段落之间没有依赖关系，可以任意调换顺序
- [ ] **反射性结构**：背景介绍 → 问题 → 解决方案 → 总结，机械套用无差别

**判断标准**：如果每个章节的标题都能完整概括该章节的内容，且章节之间互不依赖，则属于目录/系统游览式散文。

**改进方向**：找一条贯穿全文的主线——一个具体问题、一次踩坑经历、一个让自己意外的发现——让段落互相依赖而不是独立陈列。

### 5. 虚假具体性警告

- [ ] 出现无法核实的精确数字（如"性能提升了 47%"但无测试数据）
- [ ] 出现合成引用（看起来像引用某人说的话，但无来源）
- [ ] 出现对内部机制的自信断言（"系统内部实际上是…"但无官方来源）

### 6. 声音与个性

- [ ] 文章中有没有作者自己的判断或看法（不只是陈述事实）
- [ ] 有没有承认不确定性或权衡取舍（"这个方案解决了 X，但引入了 Y"）
- [ ] 有没有体现作者的具体经历（"我在使用时遇到了…"）
- [ ] 结论是否有实质立场，还是模糊的"各有优劣"

**声音缺失的典型表现**：读完文章不知道作者对这个技术持什么态度，只知道它"有很多特性"。

**活人感终审**（通读全文后回答）：

- [ ] **温度感**：情绪表达是体感记忆还是知识性描述？「我当时就卡住了」是体感记忆，「我感到非常困惑」是知识性描述，前者更真实。
- [ ] **独特性**：有没有「只有这个博客才会写出的角度」？还是换一个 AI 内容账号也能写出差不多的东西？
- [ ] **姿态**：语气是「有经验的人在认真聊一件打动他的事」，还是悄悄滑入了「导师在教学生」的姿态？
- [ ] **心流**：通读时有没有哪个地方注意力断掉、需要回头理解逻辑？有则标出，那就是需要修的节奏断点。

### 7. 冗余削减

- [ ] 找出文章中最空洞的一句话，看是否可以删除或替换为具体内容
- [ ] 检查引言是否在第一段就说明了文章要解决什么具体问题
- [ ] 检查总结是否只是重复了正文的标题，没有增加新信息

## Report Format

审查报告按以下格式输出：

```markdown
## 文章审查报告

**文件**：`source/_posts/YYYY-MM-DD-title.md`
**审查日期**：YYYY-MM-DD

---

### Part 1：格式审查

#### 必须修改

| # | 位置 | 问题 | 建议 |
|:--|:-----|:-----|:-----|
| 1 | 第 N 行 | 问题描述 | 修改建议 |

#### 建议修改

| # | 位置 | 问题 | 建议 |
|:--|:-----|:-----|:-----|
| 1 | 第 N 行 | 问题描述 | 修改建议 |

#### 合规项

列出检查通过的格式规范项。

---

### Part 2：内容深度审查

#### 必须修改

| # | 位置 | 问题类型 | 问题描述 | 建议 |
|:--|:-----|:--------|:--------|:-----|
| 1 | 第 N 段 | AI 套话 | 具体问题 | 修改建议 |

#### 建议修改

| # | 位置 | 问题类型 | 问题描述 | 建议 |
|:--|:-----|:--------|:--------|:-----|
| 1 | 第 N 段 | 无锚段落 | 具体问题 | 修改建议 |

#### 合规项

列出检查通过的内容质量项。

---

### 总评

一段话综合评价文章的格式合规度和内容深度，指出最优先改进方向。
```

**分类标准**：

格式审查：
- 必须修改：影响发布的问题（错误路径、语病、格式错误、缺少必要结构）
- 建议修改：不影响发布但可以提升质量的问题（缺少 blockquote、段落偏长）

内容深度审查：
- 必须修改：明显的 AI 套话词汇、完全无锚的段落、虚假具体性声称
- 建议修改：声音缺失、结构过于模板化、可以更具体但不影响核心观点
