你是否遇到过这样的场景：使用 AI 编程工具时，每次开始新对话都要反复告诉它项目用的是什么框架、测试命令是什么、代码风格有什么要求？或者 AI 总是生成不符合你团队规范的代码，你不得不一遍遍纠正？这些问题的根源在于——AI 不了解你的项目。Claude Code 的 CLAUDE.md 正是为解决这个问题而生的。它是一个简单的 Markdown 文件，却能让 Claude Code 从一个通用的 AI 助手变成真正理解你项目的专属开发伙伴。本文将全面介绍 CLAUDE.md 的方方面面，包括它是什么、如何加载、怎么编写、最佳实践，以及与其他 AI 编程工具指令文件的对比。

## 什么是 CLAUDE.md

CLAUDE.md 是一个 Markdown 格式的文件，Claude Code 在每次会话开始时会自动读取它。你可以在这个文件中编写各种指令、规则和偏好设置，Claude Code 在后续的交互中会遵循这些指令来工作。

Reddit 上曾有一张广为流传的 meme，用 2024 巴黎奥运会射击比赛的对比图来调侃 Claude Code 的用户分为两类——左边是全副武装、疯狂安装各种插件的选手，右边是单手插兜、只靠一个 CLAUDE.md 就淡定搞定一切的土耳其神射手：

{% img /images/post/2026/02/claudemd1.png 1000 600 %}

虽然这只是一个玩笑，但它揭示了一个事实：与其折腾各种花哨的插件配置，不如花时间写好一个 CLAUDE.md。那些精心编写 CLAUDE.md 的用户，往往能获得远超预期的使用体验，因为 CLAUDE.md 从根本上改变了 AI 与你的项目交互方式。

打一个形象的比喻：如果你把 Claude Code 想象成一位新加入你团队的开发者，那么 CLAUDE.md 就是你给他的**项目入职手册**。没有这份手册，这位新同事需要反复询问各种基础问题——项目怎么构建？用什么测试框架？代码风格是什么？有了这份手册，他从第一天起就能按照团队的方式高效工作。

> **CLAUDE.md 的核心价值：** 将 Claude Code 从一个通用 AI 助手，变成针对你项目定制的专属开发工具。

## CLAUDE.md 的加载顺序

CLAUDE.md 并不是只有一个文件，而是一个多层级的文件体系。Claude Code 会按照特定的顺序加载不同位置的 CLAUDE.md 文件，让你可以在不同层面设置指令。

### 文件层级体系

下面是 CLAUDE.md 文件的完整层级结构：

| 类型       | 文件位置                                                     | 用途                     | 共享范围                 |
| ---------- | ------------------------------------------------------------ | ------------------------ | ------------------------ |
| 组织级策略 | `/Library/Application Support/ClaudeCode/CLAUDE.md`（macOS） | IT/DevOps 统一管理的指令 | 组织内所有用户           |
| 用户级     | `~/.claude/CLAUDE.md`                                        | 个人偏好，所有项目生效   | 仅个人                   |
| 用户级规则 | `~/.claude/rules/*.md`                                       | 个人的模块化规则         | 仅个人                   |
| 项目级     | `./CLAUDE.md` 或 `./.claude/CLAUDE.md`                       | 团队共享的项目指令       | 团队（通过版本控制）     |
| 项目规则   | `./.claude/rules/*.md`                                       | 模块化的项目规则         | 团队（通过版本控制）     |
| 项目本地   | `./CLAUDE.local.md`                                          | 个人的项目特定偏好       | 仅个人（自动 gitignore） |
| 子目录     | `./子目录/CLAUDE.md`                                         | 子目录专属指令           | 团队（通过版本控制）     |

在日常使用中，最常用的是**项目级**的 `./CLAUDE.md`，它通过版本控制与团队共享，是团队协作的核心配置。

### 加载规则

Claude Code 在启动时遵循以下加载规则：

- 工作目录**及其上方**目录中的 CLAUDE.md 文件在启动时**完整加载**
- **子目录**中的 CLAUDE.md 文件**按需懒加载**——只有当 Claude 读取该子目录中的文件时才会加载
- **更具体的指令优先于更广泛的指令**：项目级指令优先于用户级，子目录指令优先于根目录
- 项目规则（`.claude/rules/`）的优先级与项目级 CLAUDE.md 相同

### 冲突解决

当不同层级的 CLAUDE.md 文件中出现冲突指令时，Claude Code 遵循**就近原则**——更具体的指令覆盖更宽泛的指令。例如，如果用户级 CLAUDE.md 写了「使用 4 个空格缩进」，而项目级 CLAUDE.md 写了「使用 2 个空格缩进」，那么在该项目中 Claude Code 会使用 2 个空格缩进。

### @imports 引用机制

CLAUDE.md 支持通过 `@` 符号引用其他文件，这是实现模块化管理的关键能力。

```markdown
# Project Instructions

See @README.md for project overview.
See @package.json for available npm commands.

# Detailed Guidelines

- Git workflow: @docs/git-instructions.md
- API design: @docs/api-guidelines.md
```

- `@` 路径支持**相对路径和绝对路径**，相对路径基于包含 import 的文件来解析
- 支持 `@~/` 前缀引用 home 目录中的文件，例如 `@~/.claude/my-project-rules.md`
- 被导入的文件还可以**递归导入**其他文件，最大递归深度为 **5 层**
- Markdown 代码块中的 `@` 引用不会被当作 import 解析，所以 `` `@anthropic-ai/claude-code` `` 这样的包名不会被误认为是 import

> **注意：** 项目中首次遇到外部 import 时，Claude Code 会弹出审批对话框让你确认。这是一个一次性的决定——一旦拒绝，该 import 将被永久跳过，不会再次询问。

## 如何编写 CLAUDE.md

### 使用 /init 命令快速开始

最简单的起步方式是在项目根目录下运行 Claude Code 的 `/init` 命令。Claude Code 会分析你的项目结构，自动生成一个包含基础信息的 CLAUDE.md 文件：

```bash
$ claude
> /init
```

`/init` 会检测项目的技术栈、常用命令、目录结构等信息，生成一个初始版本。不过这只是起点，你需要根据团队的实际情况来完善它。

### 核心内容清单

一个好的 CLAUDE.md 通常包含以下几类内容：

**1. 项目概述**

```markdown
# My Project

基于 Next.js 14 的电商平台，使用 TypeScript 开发，后端采用 tRPC + Prisma + PostgreSQL。
使用 Turborepo 进行 monorepo 管理。
```

**2. 常用命令**

```markdown
## Commands

- Build: `npm run build`
- Test all: `npm run test`
- Test single: `npm run test -- path/to/test`
- Lint: `npm run lint`
- Dev server: `npm run dev`
- Database migration: `npx prisma migrate dev`
```

**3. 编码规范**

```markdown
## Code Style

- Use 2-space indentation
- Prefer named exports over default exports
- Use `interface` over `type` for object shapes
- File naming: kebab-case for files, PascalCase for components
- Always use explicit return types for functions
```

**4. 项目特殊注意事项（Gotchas）**

```markdown
## Gotchas

- The `user` table uses soft delete, always filter by `deleted_at IS NULL`
- API routes under `/api/v2/` require the new auth middleware
- Don't modify files in `src/generated/` — they are auto-generated by Prisma
```

**5. 工作流程**

```markdown
## Workflow

- Create a new branch for each feature: `feat/description`
- Run `npm run test` before committing
- PR must include tests for new features
- Use conventional commits: `feat:`, `fix:`, `chore:`, etc.
```

### 完整示例

下面是一个综合的 CLAUDE.md 示例：

```markdown
# E-Commerce Platform

Full-stack e-commerce application built with Next.js 14, TypeScript,
tRPC, Prisma, and PostgreSQL. Monorepo managed by Turborepo.

## Commands

- Build: `pnpm build`
- Test: `pnpm test`
- Test single: `pnpm test -- --filter=@app/web`
- Lint: `pnpm lint`
- Format: `pnpm format`
- Dev: `pnpm dev`

## Code Style

- Use 2-space indentation for all files
- Prefer named exports
- Use `interface` for object shapes, `type` for unions/intersections
- File naming: kebab-case (e.g., `user-profile.tsx`)
- Component naming: PascalCase (e.g., `UserProfile`)
- Always add explicit return types to exported functions

## Architecture

- `packages/web` — Next.js frontend
- `packages/api` — tRPC API layer
- `packages/db` — Prisma schema and migrations
- `packages/shared` — Shared types and utilities

## Gotchas

- The `users` table uses soft delete — always filter `deleted_at IS NULL`
- Files in `packages/db/generated/` are auto-generated, do not edit
- API v2 routes require the new JWT middleware in `packages/api/middleware/auth-v2.ts`

## Workflow

- Branch naming: `feat/xxx`, `fix/xxx`, `chore/xxx`
- Run `pnpm test` and `pnpm lint` before committing
- Use conventional commits
- PRs require at least one approval
```

这个示例覆盖了项目概述、常用命令、编码规范、架构说明、特殊注意事项和工作流程。Claude Code 读取后就能像一个了解项目的团队成员一样工作。

## CLAUDE.md 如何演进

CLAUDE.md 不是一次写完就结束的文件，它应该随着项目一起成长。

### 从基础版本开始

使用 `/init` 命令生成初始版本后，不要急着把所有规则都写进去。先从最基础的内容开始——项目描述、构建命令、基本的代码风格要求。

### 根据摩擦点逐步完善

在实际使用 Claude Code 的过程中，你会发现一些反复出现的问题：

- Claude 总是用 `npm` 而不是 `pnpm`？添加一条指令
- Claude 生成的测试文件放错了目录？明确测试文件的存放规则
- Claude 不知道某个模块不能直接修改？在 Gotchas 中记录

**每次遇到需要手动纠正 Claude 的情况，就是完善 CLAUDE.md 的好时机。**

### 利用 Insights 报告优化

Claude Code 会根据你的使用习惯生成 insights 报告，其中会包含关于 CLAUDE.md 的优化建议。例如，它可能会发现你经常告诉 Claude 使用某种特定的测试模式，然后建议你把这个偏好写入 CLAUDE.md。

### 推荐的演进路径

1. **起步阶段**：用 `/init` 生成基础版本，添加最常用的命令和规则
2. **磨合阶段**：在日常使用中发现问题，逐条添加规则
3. **成熟阶段**：规则积累到一定数量后，开始用 `.claude/rules/` 做模块化拆分
4. **精简阶段**：定期审查，删除过时的规则，合并重复的指令

## CLAUDE.md 最佳实践

### 保持简洁

CLAUDE.md 的内容会占用上下文窗口（context window）的 token，过长的文件会减少 Claude Code 可用于实际编码任务的上下文空间。建议将主 CLAUDE.md 文件控制在 **150 行以内**，如果内容较多，使用 `@imports` 引用详细文档。

### 使用渐进式披露

不要把所有内容都塞进一个文件。利用多层级文件体系和 `@imports` 来组织内容：

```markdown
# Project Overview

Brief description here.

## Commands

Common commands here.

## Detailed Guidelines

- Code style: @docs/code-style.md
- Testing guide: @docs/testing-guide.md
- API conventions: @docs/api-conventions.md
```

这样主文件只包含高频信息，详细内容按需加载。

### 模块化管理

善用 `.claude/rules/` 目录按主题拆分规则：

```
.claude/rules/
├── code-style.md      # code style rules
├── testing.md         # testing conventions
├── security.md        # security requirements
├── git-workflow.md    # git workflow rules
└── frontend/
    ├── react.md       # React specific rules
    └── styles.md      # CSS/styling rules
```

还可以使用条件加载，让规则只在处理特定文件类型时生效：

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules

- All API endpoints must include input validation
- Use zod for request schema validation
```

### 手动编写，不要全自动生成

`/init` 只是一个起点。自动生成的内容往往过于笼统，缺少项目真正独特的知识。比如，只有你的团队知道「`user` 表用了软删除」，或者「`/api/v2` 路由需要新的认证中间件」——这些关键信息必须手动添加。

### 不要放敏感信息

这一点怎么强调都不过分：**绝对不要**在 CLAUDE.md 中放置 API key、密码、token 或任何敏感凭据。CLAUDE.md 通常通过版本控制共享，这意味着其中的内容对所有有仓库访问权限的人可见。如果有不想共享的个人偏好，请使用 `CLAUDE.local.md`——它会被自动添加到 `.gitignore`。

### 传达意图，而不仅仅是规则

好的 CLAUDE.md 不只是一份规则清单，它应该传达项目的意图和设计决策背后的原因：

```markdown
# 不够好的写法

- Use PostgreSQL

# 更好的写法

- Use PostgreSQL for all data storage. We chose PostgreSQL over MongoDB
  because our data is highly relational and we need ACID transactions
  for payment processing.
```

当 Claude Code 理解了 **WHY**，它在遇到规则未覆盖的场景时也能做出更合理的决策。

### 持续迭代

每隔一段时间审查一次 CLAUDE.md，删除不再适用的规则，更新过时的命令，确保内容与项目当前状态一致。一个过时的 CLAUDE.md 可能比没有 CLAUDE.md 更糟糕——它会让 Claude Code 按照错误的信息行事。

## CLAUDE.md 的不足和改进

尽管 CLAUDE.md 是一个强大的配置机制，但它目前仍存在一些已知问题。

### 子目录加载的局限性

子目录中的 CLAUDE.md 采用懒加载策略——只有当 Claude 读取该子目录中的文件时才会加载。这意味着如果你在子目录中定义了重要的规则，但 Claude 在该会话中没有访问该子目录的文件，这些规则就不会生效。

### 文件名不统一

在 AI 编程工具的生态中，不同工具使用不同的指令文件名——Claude Code 用 `CLAUDE.md`，Codex CLI 用 `AGENTS.md`，Cursor 用 `.cursorrules`。这种不统一给使用多个工具的开发者带来了额外的维护成本。社区中已经有声音呼吁将 `AGENTS.md` 作为统一标准，不过目前各家厂商仍然各自为政。

### 上下文窗口占用

CLAUDE.md 的内容会占用宝贵的上下文窗口空间。如果文件过长，留给实际编码任务的上下文就会减少。虽然可以通过 `@imports` 和模块化来缓解这个问题，但在根本上仍然存在信息量和上下文空间之间的权衡。

### Auto Memory 的限制

Claude Code 的 Auto Memory 功能（自动记忆使用习惯到 `MEMORY.md`）只加载前 200 行内容。当自动记忆累积到超过 200 行时，超出的部分在会话启动时不会被加载。

### 学习要点

在参考这些项目时，建议重点关注以下几点：

- **结构组织**：好的 CLAUDE.md 通常层次分明，使用清晰的标题和分组
- **信息密度**：每一条规则都有具体的价值，避免泛泛而谈
- **模块化程度**：大型项目如何利用 `.claude/rules/` 目录和 `@imports` 来管理复杂的规则体系
- **团队协作**：如何平衡团队共享指令和个人偏好（`CLAUDE.md` vs `CLAUDE.local.md`）

## 对标其他同类产品的文件

CLAUDE.md 并非 AI 编程工具中指令文件的唯一实现。随着 AI 编程工具的爆发式增长，几乎每个工具都推出了自己的指令文件方案。

### 指令文件对比

| 工具        | 指令文件             | 提供商    |
| ----------- | -------------------- | --------- |
| Claude Code | CLAUDE.md            | Anthropic |
| Codex CLI   | AGENTS.md / codex.md | OpenAI    |
| Gemini CLI  | GEMINI.md            | Google    |
| Cursor      | .cursorrules         | Cursor    |

### 各自特点

- **CLAUDE.md**：多层级文件体系、`@imports` 引用机制、`.claude/rules/` 条件加载，功能最为完善
- **AGENTS.md**：OpenAI 推出的开放标准提案，旨在成为跨工具的通用格式，支持 frontmatter 中定义触发条件
- **GEMINI.md**：Google Gemini CLI 的指令文件，设计理念与 CLAUDE.md 类似，支持多层级加载
- **.cursorrules**：Cursor 编辑器早期采用的格式，社区生态丰富，但功能相对简单

### 关于统一标准

目前 AI 编程工具的指令文件处于「各自为政」的状态，这对使用多个工具的开发者来说增加了不少维护成本。OpenAI 提出的 `AGENTS.md` 试图成为行业通用标准，一些工具已经开始兼容这个格式。从长远来看，社区可能会逐步收敛到一个统一标准上，但这需要各厂商的共同努力。在那之前，如果你同时使用多个 AI 编程工具，可能需要维护多份类似但不完全相同的指令文件。

## 总结

本文全面介绍了 Claude Code 的 CLAUDE.md 文件——从基本概念到多层级加载机制，从编写方法到最佳实践。CLAUDE.md 的核心价值在于将 Claude Code 从一个通用的 AI 助手变成你项目的专属开发工具，而实现这一转变只需要投入一点时间来编写和维护一个 Markdown 文件。

在实际使用中，建议从 `/init` 命令生成的基础版本开始，随着使用过程中遇到的问题逐步完善，最终形成一套适合你团队的规则体系。记住，好的 CLAUDE.md 不是一蹴而就的，而是在持续迭代中逐渐成熟的。如果你还没有开始使用 CLAUDE.md，现在就是最好的时机——它可能是你在 AI 编程工具上做的最值得的配置投资。
